## 1. 设计目标与非目标

### 目标

| 目标 | 具体含义 |
|---|---|
| **可遗忘** | 记忆有梯度地淡出，永不归零。不是「全留」或「全删」。 |
| **可解释** | 每次检索都能回答「为什么想起这条」。返回 evidence / score / 三路分项。 |
| **有结构** | 流水不是事实，事实不是约定，约定不是做法。分型分层存。 |
| **可移植** | 数据就是 JSON，换机器 `cp -r` 就行。没有向量数据库、没有外部服务。 |
| **中文优先** | 分词、稀有度、意图识别都按中文设计，不是英文方案加个中文壳。 |

### 非目标

| 非目标 | 理由 |
|---|---|
| 开箱即用的聊天插件 | 这是库，不是应用。接入方式千差万别。 |
| 多租户隔离 | 一个 store 一个目录，隔离靠目录，不靠逻辑。 |
| 并发安全 | 单进程独占。多进程写同一目录会互相覆盖（已知边界）。 |
| 分布式 / 云同步 | 陪伴场景的记忆应该留在本地。 |
| 替代上下文窗口 | 它是对上下文的补充，不是替换。窗口内的事不需要查库。 |

## 2. 数据模型

### 三层 × 四型

**层（layer）决定衰减速度**：

```js
export const LAYER_CONFIG = {
  core:    { halfLifeDays: Infinity, max: 400,  decayAlpha: 0    },
  long:    { halfLifeDays: 180,      max: 3000, decayAlpha: 0.35 },
  working: { halfLifeDays: 21,       max: 6000, decayAlpha: 0.9  },
};
```

| 层 | 语义 | 例子 |
|---|---|---|
| `core` | 永不衰减，永不裁 | 「他是我主人」「我叫小鲸鱼」 |
| `long` | 提炼过的事实/画像/偏好 | 「他不抽烟」「他喜欢先给结论」 |
| `working` | 流水、待办、想说没说 | 「今天下午聊了训练进度」 |

**型（kind）决定去哪张表**：

```js
export const MEMORY_KINDS = [
  'episodic',   // 谁在哪天说了什么（流水）
  'semantic',   // 提炼过的事实
  'pending',    // 想说但没说出口（会过期）
  'core',       // 核心身份
  'profile',    // 某个人的画像
  'procedural', // 学会的做法（单独一个文件）
];
```

层和型是正交的：一条 `semantic` 可以在 `long` 层，也可以在 `working` 层。

### 存储布局

```
<dir>/
├── semantic.jsonl          语义层（一行一条，只增不删）
├── pending.json            未说出口（会过期）
├── procedural.json         程序记忆
├── index.json              巩固水位 / 统计
├── semantic-space.json     LSA 语义空间缓存
├── episodic/
│   ├── 2026-10-24.jsonl    按天分册
│   └── 2026-10-28.jsonl
└── cold/
    └── 2026-10.jsonl       沉底的，按月份归档
```

**为什么用 JSONL 而不是 SQLite：**

| | JSONL | SQLite |
|---|---|---|
| 人可读 | ✓ 直接 cat / grep | ✗ 要工具 |
| 增量写 | ✓ append 一行 | ✓ |
| 部分损坏 | ✓ 坏一行只丢一行 | 看情况 |
| 迁移 | ✓ cp -r | ✓ |
| 并发 | ✗ | ✓ |
| 大规模 | ✗ 全量读进内存 | ✓ 索引 |

选择 JSONL 是因为：**陪伴场景的记忆量级是几百到几千条**，全量读进内存没问题，而"人能直接打开看自己的记忆"这件事的价值远大于并发和大规模。

规模上界：按每天 60 条算，一年 2.2 万条。到那个量级仍能全量读（几十 MB）。

### 一条记忆的字段

```js
{
  id: 'a37a4054',          // 内容哈希
  text: '...',
  kind: 'semantic',
  layer: 'long',
  who: 'Pure White',       // 关于谁（写入时清零宽字符）
  where: '',               // 在哪
  tags: ['性格'],
  importance: 4,           // 1~5
  hits: 0,                 // 被召回次数
  emotion: 1.0,            // 情绪权重
  createdAt: 1792860133580,
  lastHitAt: 0,
  source: 'consolidate',   // migrate | ai | consolidate | replay | local-digest
  attr: '',                // 属性键（profile.city / pref.like）用于冲突检测
  derivedFrom: [...],      // 溯源：哪些原始消息推出来的
  mergedFrom: [...],       // 被合并进来的 id（合并后 hits/importance 已累加）
}
```

## 3. 写入路径

```
消息 → 分词 → 编码门控 → 分流到对应存储
```

### 编码门控（`memory-attention.js`）

人不会记住别人说的每句话，只有"引起注意"的才编码进海马体。

```js
shouldEncodeEpisode(text, { self, where, vocab, recentMaxSim })
// → { keep, weight, reason }
```

刻意保守——**宁可多留，不可误杀**。只有三种情况丢：

| 情况 | 判据 |
|---|---|
| 纯噪声 | 只有标点/符号 |
| 纯占位 | 只有 `[表情]` `[图片]` `[转发消息 id=...]` |
| 垃圾消息 | 频道公告、系统提示 |

短句和 self 消息落盘但**降权**，不丢。

### 分配重要度

```js
importance = clamp(
  base * emotionWeight(text) + 长度加成 + 关键词加成,
  1, 5
)
```

关键词命中示例：`永远记住|答应|约定|第一次|生日|吵架|道歉|骗|委屈` 会加分。

## 4. 读取路径

这是整个系统最复杂的部分。

### 流程

```
query
  ├─ parseCues        剥掉指代（「那个」「上次说的」），留真语义内容
  ├─ segmentCached    词表分词
  ├─ 双尺子筛线索      通用中文稀有 × 库内稀有
  ├─ 三路打分          字面 / 语义 / 记忆分
  ├─ 证据门槛          evidence < gate → 丢
  ├─ 干扰竞争          跟已入选的太像就压分
  └─ top-k
```

### 4.1 指代剥离

```js
parseCues('你还记得上次那个猫的事情吗')
// → { temporal: true, speaker: false, asking: true, core: '猫 事情' }
```

为什么要单独做：`「上次」「那个」「你说的」` 本身没有语义值，但它们**指向时间**或**指向说话人**。BM25 对它们完全无能为力（全是高频词），向量也一样。

### 4.2 双尺子线索筛选

```js
isCue(word) = !疑问词表.has(word)
           && (意图词表.has(word) || universalRarity(word) >= 0.34)
```

**疑问词黑名单**：`怎么样 / 什么 / 几点 / 什么时候 / 是否 / 这个 / 那个 / 东西 / 事情 / 时候 …`

为什么单独列表而不靠词频自动挡：**「怎么样」在 jieba 词频里是 0.48——过了 0.34 那道门**，因为它是三字词、比「什么」(0.26) 罕见。可它一点信息量都没有。

实测后果：查「外面天气怎么样」，一条内容就是「怎么样」三个字的残片拿到 `evidence=0.3069` 排第一——它命中了 3 个线索词里的 1 个，而饱和曲线只看绝对量。

**意图词白名单**：`喜欢 / 讨厌 / 答应 / 承诺 / 约定 / 要求 / 生气 / 难过 …`

为什么需要：`通用门槛=0.34` 会把「喜欢」(0.38) 挡在外面——而它在陪伴场景里是**最核心的线索词**。实测后果：「你还记得我喜欢什么吗」切完只剩「记得」一个，跟记忆「他喜欢蓝色小鲸鱼」的「喜欢」对不上。

「表示」「正式」是 0.34~0.39 那档必须挡；「喜欢」0.38 必须留。两者数值几乎重叠，说明**光靠词频表分不开**。

### 4.3 三路打分

```js
字面   = bm25[i] / max(bm25)                              // 0~1
语义   = max(0, lsa_cos) * 0.62 + max(0, ngram_cos) * 0.38
记忆分 = scoreMemory(m) / max(scoreMemory)                 // 0~1

score = 字面 * 0.34 + 语义 * 0.36 + 记忆分 * 0.30
      + 系列位置加成 + 情绪一致加成
```

**语义权重略高于字面**：字面命中时语义一般也高，两路互相印证不会误伤精确查询；而「字面没命中、语义命中」恰恰是最有价值的一类，只有抬语义才捞得回来。

### 4.4 证据门槛（核心）

```js
evidence = 命中词的 (库内稀有 × 通用稀有 × 单字降权) 之和
         → 过饱和曲线 s / (s + 1)
         → 若问时间且这条讲时间，+0.15
```

**为什么门槛必须卡 evidence 而不是 score：**

`score` 里含 `记忆分`，而记忆分随重要度和衰减变化。拿它当"够不够相关"的门槛，等于「一条老记忆因为不够新鲜就被判定为不相关」。

实测：把 `unknownActivation` 从 1 调到 0.75，该想起的从 10/11 掉到 8/11。

分开之后：门槛只管「有没有真关系」，重要度/衰减**只参与排序**。

**为什么库内稀有度用对数式：**

```js
// ❌ 线性：小库会崩
1 - df / (N * 0.25)
// N=3, df=1 → 1 - 1/0.75 = -0.33 → 归零

// ✓ 对数：小库给 0.5
log((N+1)/(df+1)) / log(N+1)
```

而且 `N < 20` 时直接返回 1——统计不显著时不该拿它压分。

**为什么单字要降权 0.35：**

「富江」被切成 `富 | 江`。单字在库里 df 天然很低 → 稀有度算 1.0 → **两条只含「富江」二字的残片 evidence=0.47，比真正讲破甲那条还高**（残片短，两个字就占满饱和曲线）。

中文语义单位基本 ≥2 字，单字更多是切词残留。

**安全垫（三条）：**

```js
剩的能用 = 有词表 && q过库.length >= 1 && 有任一命中
q证据词 = 剩的能用 ? q过库 : (有词表 ? (q过通用.length ? q过通用 : q全部) : [])
```

三条都必要：

1. 筛剩 0 个 → 一个线索都没有，退回不筛
2. 筛剩的词在本库一次都没出现 → 筛错方向了，退回
3. 库太小 → 「本库太常见」那道门本来就没做，但「通用中文」那道门照样会砍

> 踩坑记录：第一版写成「不足 2 个就退回」，集成测试挂了。「你还记得我喜欢什么吗」切完只剩「喜欢」一个，不退回的话那唯一一个词 evidence 太小，整轮一条都想不起来。
> 同类项目写 `>= 2` 是因为它的切词器不会丢单字；我们这边会丢，剩 1 个是常态。

### 4.5 干扰竞争

```js
competitionPenalty(score, maxSimilarityWithSelected)
```

逐条放进去，跟已入选的比相似度，太像就压分往下沉。

这是「提取诱发遗忘」（retrieval-induced forgetting）的实现，同时天然解决同一件事 5 条变体一起挤进 prompt。

> 性能坑：原来在循环里对每条候选和每条已入选的都调 `embed(text)` 重算 n-gram 向量——563 条 × limit 次哈希，单次 recall 100ms+。实际 `vecs[i]` 已经预计算好了，直接取下标即可。

### 4.6 分档上限（可选，默认关）

```js
const 分档 = [[0.40, limit], [0.32, 4], [0.26, 3], [0, 2]];
const 本趟上限 = 分档.find(([线]) => 最高证据 >= 线)[1];
```

设计意图：不砍任何一条够格的，只规定「这一趟最多给几条」。

**但在中文长句语料上实测是亏的**——会把正确答案一起挡掉。所以默认关闭，需要时传 `evidenceBucket: true`。

这条留着的价值是：如果你想让机器人"少说话"，打开它。

## 5. 遗忘路径

### 幂律而非指数

```
recency = (1 + age_days)^(-alpha)
```

| 衰减方式 | 180 天后 | 3 年后 | 10 年后 |
|---|---|---|---|
| 指数（半衰期 180 天） | 0.5 | 0.016 | 0.000002 |
| 幂律（alpha=0.35） | 0.16 | 0.10 | 0.077 |

指数衰减会让「初恋」和「上周三吃的面」在一年后同归于尽。幂律的尾巴长，符合人脑。

依据：Anderson & Schooler (1991) 在新闻标题记忆实验中测出 `记住概率 ≈ 频率^a × 新近度^-b`。

### 三级沉降

```
active ──[importance < 0.3 且 layer=long]──→ 降级到 working
  │
  └──[score < coldThreshold 且 layer=working]──→ 冷库（status 保持 active，但不参与热检索）
        │
        └──[超过保留期]──→ 真删（可配置关闭）
```

**冷库不是删除。** 它按月份归档到 `cold/YYYY-MM.jsonl`，`searchCold()` 能捞回来——对应人脑的「看到照片就想起来了」。

### 频率不是线性加成

```js
// ❌ 正反馈陷阱
freq = Math.pow(1 + hits, 0.6)
// 想起来 → 加分 → 更容易被想起 → 头部两条冲到 84 次，其余全饿死

// ✓ 对数加成
freq = 1 + FREQ_GAIN * Math.log2(1 + hits)
// 命中 0 次 → 1.00 倍
// 命中 9 次 → 2.99 倍（原来是 3.98 倍）
```

实测：47 条语义里只有 18 条有 hits、29 条恒为 0，头部两条冲到 84 / 67 次。换对数后仍"常想起的更难忘"，但马太效应被按住。

## 6. 消化路径

### 两段式巩固

```js
async function memoryTick() {
  // ①a 本地完整巩固先跑 —— 规则抽取，零成本、毫秒级、确定性
  //     永远不会因为模型挂了而空手而归
  digestPending(memory, { markProgress: false });

  // ①b 模型巩固后跑 —— 补本地抽不出的（情绪、关系张力、隐含偏好）
  //     它读的是同一天的流水，不会跟 ①a 抢；①a 已写下的事实会被它判成「已有 → 强化」
  await consolidatePendingWithModel(memory, { ... });

  // ② 衰减 + 冷库
  memory.decay({ coldThreshold });

  // ②b 合并重复
  memory.mergeDuplicates({ threshold: 0.95 });

  // ③ 再巩固：把被反复想起的事实拿去核对
  await reconsolidateDue(memory, { limit: 3 });

  // ④ 睡眠重放（有次数预算）
  await replayNight(memory, { days: 3, rowsPerDay: 6 });
}
```

**顺序有意义**：

- ①a 先跑：模型挂了也不空手，而且它写下的 `attr` 能让 ①b 的冲突检测对上号
- ④ 最后跑：重放的原料是**已经巩固过**的日子，抢先跑只会读到没提炼的原始噪音，产出一堆假联结

**水位推进要显式请求**：`consolidateDay` 默认不推进水位。因为它是"最小巩固"——只抄每人一句情绪最重的原文，不做画像、不做习惯聚合。一旦它顺手把水位推过去，跑在它后面的完整巩固就一天都捞不到。

### 睡眠重放

把跨天碎片打乱重新拼，找「当时没注意到的联系」。

产出的 `kind: 'insight'` 必须**单独占一个工作记忆槽**。理由：实测它的分数（0.44）永远打不过同话题原话（0.64/0.63），`relevantSlots=2` 时一次都进不去——机制造出来了却从不浮现，等于没做。

## 7. 分词子系统

### 为什么必须用词表

字符 n-gram 的跨词碎片问题：

```
「明天去公园」→ 明天 / 天去 / 去公 / 公园
                ↑ 天去、去公 是跨词碎片
```

它们天生少见（语料里不会反复出现），被当成稀有线索，把"这句话有多少信息量"抬起来。

实测：某条误报的门值 1.98 → 0.59，门槛 0.8，正好从"过"变成"不过"。

### 最长匹配 + 单字兜底

```js
function segment(text) {
  // 每个位置取最长的、词表里有的那个词
  // 一个都取不到就单字兜底，兜底单字如果是虚词就丢掉
}
```

**兜底单字是关键**：老切法丢字，就是按词比对不上的原因。

```
「她的胃」  老切法 → 「胃不好」（丢了「她的」）
                    查「她的胃」只剩单字「胃」，记忆那边是「胃不」→ 对不上
```

### 词表自学习

通用词表不认识「大肥鱼」「小鲸鱼」「伊蕾娜」这类词。

算法（`scripts/learn-lexicon.mjs`）：

```js
// 候选 2~6 字 n-gram，三个条件都过
① freq >= 3                              频次
② PMI >= 4.0                             凝聚度
③ min(左熵, 右熵) >= 0.9                  自由度

// 然后去子串包含：if A 是 B 的子串 且 B.score > A.score → 去掉 A
```

**自由度为什么是关键判据：**

```
「大肥鱼」 左邻：是/叫/这/… 右邻：的/了/啊/…   熵高 → 真词
「肥鱼」   左邻：永远只有「大」              熵 0  → 只是「大肥鱼」的尾巴
```

熵高 = 邻居杂乱 = 真词；熵低 = 邻居固定 = 某词的一部分。这条能自动去掉被长词包住的尾段。

### 参数依据

| 参数 | 值 | 依据 |
|---|---|---|
| `MIN_FREQ` | 3 | 3 次以下基本是笔误或一次性说法 |
| `MIN_PMI` | 4.0 | 2.0 太松（收进「的时」「了一」），5.0 太紧（「大肥鱼」只有 4.2 被漏） |
| `MIN_ENTROPY` | 0.9 | 0.5 收进「肥鱼」「鲸鱼」尾段；1.5 漏掉「小鲸鱼」 |

### 通用门槛 0.34

| 词 | 通用稀有度 | 判定 | 理由 |
|---|---|---|---|
| 表示 | 0.34 | 挡 | 中文排 376 名 |
| 喜欢 | 0.38 | **留**（意图词白名单） | 陪伴场景核心线索 |
| 婚礼 | 0.55 | 留 | 具体 |
| 熬夜 | 1.00 | 留 | 很具体 |

## 8. 语义空间

### 为什么自己造一个

字符 n-gram 只能抓「字面挨着」：

```
问「咪咪」→ 命中含「咪咪」的 → ✓
问「我家有只猫」→ 跟「咪咪」一个 bucket 都不重合 → ✗
```

外部 embedding 模型的问题：① 一次调用几百毫秒到几秒，唤醒时每条消息都要检索，等不起；② 几百 MB 模型 + tokenizer，跟"零依赖可移植"冲突。

### LSA 三步

```
① 新词发现：从语料里长出词表（PMI × 自由度，见上一节）
② 共现矩阵：按文档共现，PPMI 加权（负值归零，Levy & Goldberg 2014）
③ 随机化 SVD：Y = MΩ → 幂迭代 Y ← M(MᵀY) → QR 正交化
```

拿到的 `U`（V×k）就是每个词的语义向量——这正是 LSA 的 term space。

### 为什么要先用真词

直接拿 2-gram 当词是行不通的。实测会切出「我老」「的咪」「会喜」，算出来的最近邻全是自己的位置影子（`咪咪 → 的咪:1.000`），语义被噪声盖死。

### 诚实标注

这不预训练模型，是**从你自己的语料里长出来的**语义空间。

| 好处 | 代价 |
|---|---|
| 零依赖 | 语料少时（< 60 篇）向量不稳 |
| 可迁移（换机器只要搬 `state/`） | 需要先跑一遍新词发现 |
| 完全可解释（能反查哪些共享上下文把两个词拉近） | 语义质量不如 bge-m3 |

所以：`< MIN_DOCS` 时自动退回 n-gram，不拿半成品冒充。

## 9. 工作记忆

人一次只能同时想着 4 件事左右（Miller 的 7±2 是上限，恋爱场景更窄）。

```js
gatherWorkingMemory(query, { who, episodicHours, relevantSlots })
```

| 槽 | 内容 | 位置 |
|---|---|---|
| `core` | 核心身份 + 对这个人的画像 | 永远最前 |
| `recent` | 最近 24 小时权重最高的一条情景 | |
| `relevant` | 检索命中的相关记忆 | relevantSlots 个 |
| `procedural` | 学过的做法 | 有才出现 |
| `milestone` | 里程碑（我是谁） | 有才出现 |
| `insight` | **重放产出的跨天联想** | 单独一槽 |
| `faint` | 话到嘴边 | 其他都空时补 |

### 为什么 insight 要单独一槽

实测：重放产出的联想分数 0.44，同话题原话 0.64 / 0.63。`relevantSlots=2` 时它**一次都进不去**。

机制在跑但从不浮现 = 没做。

### 为什么这里要关掉 evidenceGate

```js
const hits = recall(out.query, {
  ...,
  evidenceGate: 0,   // ⚠ 必须关
});
```

因为工作记忆要装的恰恰是「字面对不上但该想起来」的东西：

- `insight` 是重放产出的跨天联想，跟 query 字面只对上一个词
- 舌尖、冷库那些也是「有痕迹但提不出来」，字面本来就不该强

门槛是给「注入 k 条省 token」用的（减少乱提旧事），工作记忆是四五个固定槽，不需要靠它省。**两件事分开。**

## 10. 性能

实测数据（232 条语义 + 2698 条情景，Windows / Node 24）：

| 操作 | 耗时 | 备注 |
|---|---|---|
| `recall(limit=6)` | p50 65ms | 含 BM25 + LSA + 三路融合 |
| `recall` 冷启动 | ~150ms | 首次构建索引 |
| 分词（缓存命中） | < 1ms | 4000 条缓存 |
| 分词（冷） | ~43ms / 850 条 | 首次 |
| LSA 空间构建 | ~2s | 只在语料变化时重建，落盘缓存 |
| `mergeDuplicates` | ~30ms / 232 条 | O(n²) bigram 比对 |

### 缓存在哪

| 缓存 | 位置 | 失效条件 |
|---|---|---|
| BM25 索引 | 内存 | 文档数变化 / 15 秒超时 |
| n-gram 向量 | 内存 | 同上 |
| LSA 空间 | `semantic-space.json` | 语料变化 |
| 分词结果 | 内存 Map（4000 条） | 满了整个丢掉重建 |

### 已知瓶颈

1. **`mergeDuplicates` 是 O(n²)**。232 条 30ms，2000 条约 2s，5000 条约 13s。超过几千条时建议加 LSH 或按 `who` 分桶。
2. **全量读 JSONL**。每次 `createMemoryStore` 会把所有语义记忆读进内存。万级以上需要改成按需加载。
3. **LSA 全量矩阵**。语料变化时重建整个空间，大语料会卡。

## 11. 被否决的设计

记录下来，免得以后有人重新发明这些坑。

### ❌ 门槛卡总分

```js
if (score < 0.3) 丢掉   // score 含重要度和衰减
```

问题：记忆分的任何调整都会整体平移全库分数，连着"该想起的"一起被挡掉。
→ 改成门槛卡 evidence，重要度只参与排序。

### ❌ 相对门槛砍结果

```js
if (score < 0.7 * 最高分) 丢掉   // 想"分数低 = 不相关"
```

实测误杀：四条不同的事里，撞得强的 0.667、另外两条 0.358，相对线画到 0.467，把该进来的砍了。

教训：**分数低不等于不相关**，只是那条撞得没那么准。不能拿相对分砍。

### ❌ 碎片覆盖惩罚

想压掉「怎么样」这种三字残片命中：按「命中词占该条记忆的比例」打折。

结果：把评分打散，`recall@3` 从 75% 掉到 50%，平均返回条数掉到 1.9。方向对但实现方式错了。
→ 撤销。改用疑问词黑名单，从源头解决。

### ❌ 单用 n-gram 找重复

用「三字片段相似度 ≥ 0.85」判重。

实测在真库里一对都抓不到：

```
同一件事的一对（一条 220 字、一条 146 字）→ 只有 0.706
其它同一件事的对 → 大多落在 0.33~0.83
```

原因：两句话只要换几个字，整串三字片段就全错位（「她不是」「不是胃」「是胃寒」全是跨词边界碎片）。
→ 改成按词比。

### ❌ 合并阈值 0.92

实测开始把「同一天的两件不同的事」并成一条。那是不可逆的信息损失。
→ 0.95，只抓「几乎逐字相同」。

## 12. 调参指南

### 最常调的几个

| 参数 | 位置 | 默认 | 什么时候改 |
|---|---|---|---|
| `evidenceGate` | `recall()` | 0.15 | 答案太杂→调高；一条都不给→调低 |
| `evidenceBucket` | `recall()` | false | 想让机器人少说话→true |
| `limit` | `recall()` | 8 | 注入条数上限 |
| `threshold` | `mergeDuplicates()` | 0.95 | 重复太多→降到 0.93（别更低） |
| `coldThreshold` | `decay()` | 0.06 | 冷库太快→调低 |
| `FREQ_GAIN` | `memory-core.js` | 0.6 | 头部记忆垄断→调低 |

### 怎么调才不翻车

**这是本项目血泪教训**：

1. **留两套评测集。** 一套用来调参，一套**绝不参与调参**。只有两套都好才是真好了。
2. **一次只动一个参数。** 改两个就看不出是哪个起作用。
3. **别照抄别人的数值。** `evidenceGate=0.30` 在短句语料上是对的，在长句语料上会把正确答案全挡掉。同一个数字搬到不同分布上就是错的。
4. **改动做成可关的开关。** 这样发现亏了能立刻关掉，不用回滚代码。

### 快速自检

```bash
npm test          # 13 个测试
npm run demo      # 看端到端行为
```

如果 `demo` 里「外面天气怎么样」返回了结果，说明 **疑问词黑名单没生效**——去查 `memory-lexicon.js` 的 `isCue`。
